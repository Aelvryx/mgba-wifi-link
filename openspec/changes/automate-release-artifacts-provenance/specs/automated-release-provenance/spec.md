## ADDED Requirements

### Requirement: An approved annotated tag starts the complete release

The project SHALL treat a new canonical annotated `vMAJOR.MINOR.PATCH` tag pushed
by an authorized maintainer as a trusted release instruction. One workflow SHALL
perform every later validation, build, package, and publication step without a
manual dispatch, asset upload, approval pause, or Publish click.

#### Scenario: Approved tag is pushed
- **WHEN** an authorized maintainer pushes a valid annotated version tag
- **THEN** the complete automated release starts and requires no later human gate

#### Scenario: Tag is invalid
- **WHEN** the tag is lightweight, malformed, missing reviewed notes, version-
  inconsistent, or does not peel to the intended `master` history
- **THEN** the workflow fails before building or publishing release assets

### Requirement: The maintainer tag is inside the project trust boundary

The release workflow SHALL trust the authorized maintainer and deliberately
pushed tag. It MUST NOT add a protected-controller, hostile-tag defense,
governance credential, or equivalent system whose purpose is to defend the
repository from that maintainer rewriting their own workflow.

#### Scenario: Trusted maintainer approves a release
- **WHEN** the repository owner deliberately creates and pushes the release tag
- **THEN** ordinary repository access control is the trust boundary and the tag
  workflow may execute the reviewed release process

### Requirement: Release evidence belongs to the exact tagged source

The workflow MUST execute the existing normal, ASan/UBSan, TSan, complete-suite,
fixture/tooling, and Android/binary-boundary gates against the peeled tag commit.
It SHALL record exact run/job conclusions and MUST reject missing, failed,
cancelled, skipped, ambiguous, or wrong-source evidence.

#### Scenario: Every required gate passes
- **WHEN** all required protected jobs pass for the peeled commit
- **THEN** packaging may consume that exact evidence and Android artifact

#### Scenario: Evidence is incomplete
- **WHEN** a required job is absent, unsuccessful, or belongs to another commit
- **THEN** no release draft or public release is created

### Requirement: Independent Android builds are byte-reproducible

The workflow SHALL build the Android ARM64/API 21 core twice in independent clean
jobs using the same pinned configuration and MUST require byte-identical non-empty
outputs with the same SHA-256.

#### Scenario: Both builds match
- **WHEN** both clean builds complete with identical bytes
- **THEN** one verified core is admitted to packaging

#### Scenario: Builds differ
- **WHEN** either build fails or the outputs differ by any byte
- **THEN** publication stops before a release draft is created

### Requirement: The executable identity is validated

The admitted core MUST be a non-empty AArch64 ELF containing the peeled commit,
expected project version, canonical product identity, and exact protocol-v2
compatibility identity.

#### Scenario: Executable identities agree
- **WHEN** the core architecture and embedded identities match release metadata
- **THEN** deterministic packaging may proceed

#### Scenario: Executable identity conflicts
- **WHEN** any required architecture or identity check fails
- **THEN** no package or release is published

### Requirement: Release packaging is deterministic and exact

The packager SHALL normalize ordering, timestamps, modes, serialization, and ZIP
metadata. It MUST emit exactly the declared seven public assets and exact archive
members, and MUST reject missing, extra, duplicate, renamed, symlinked, traversal,
absolute, or unsafe-mode entries.

#### Scenario: Identical inputs are packaged twice
- **WHEN** two clean packaging runs consume identical admitted inputs
- **THEN** every corresponding generated byte is identical

#### Scenario: Package membership is unsafe
- **WHEN** an undeclared or malformed public asset or archive member is present
- **THEN** package verification fails before publication

### Requirement: Provenance and checksum scopes are explicit and acyclic

Canonical build and release provenance SHALL record repository, annotated tag
object, peeled source commit, first-run workflow/run/job evidence, toolchain,
configuration, and asset identities. Internal and standalone SHA-256 manifests
MUST cover their exact declared non-recursive scopes. Signed attestations SHALL
NOT be required by this capability.

#### Scenario: Provenance surfaces agree
- **WHEN** the manifests, archive, human notice, release body, and executable are
  verified
- **THEN** every shared identity and checksum agrees

#### Scenario: Provenance is incomplete or recursive
- **WHEN** a required identity is missing or a manifest attempts to hash itself or
  its enclosing archive
- **THEN** packaging fails

### Requirement: Automated publication preserves the privacy boundary

The workflow MUST publish only allow-listed public files and fields. It SHALL
reject ROM/BIOS identities, saves, raw inputs, endpoint logs, commercial evidence,
device/network identities, private paths, secrets, symlinks, and undeclared data
with bounded non-sensitive failure categories.

#### Scenario: Private material reaches staging
- **WHEN** any prohibited field, file, path, or synthetic privacy canary appears
- **THEN** the workflow fails before upload

### Requirement: GitHub operations use supported bounded interfaces

GitHub CLI/API operations SHALL use command-specific supported argument arrays,
bounded duplicate-safe JSON parsing, and bounded no-follow downloads. Production
operations MUST NOT use shell interpolation or options unsupported by the real
installed CLI.

#### Scenario: Remote evidence is malformed or oversized
- **WHEN** GitHub returns duplicate, deep, oversized, decompression-bomb, unknown,
  or otherwise malformed release evidence
- **THEN** verification fails with a bounded category and removes partial local
  downloads without mutating the release

### Requirement: Public release creation is transactional and automatic

After local verification, the publisher SHALL create a private draft, upload
exactly seven assets, read the remote state back, verify tag, target, body,
classification, inventory, size, and digest, and publish automatically. A safe
pre-publication failure MAY delete only the private draft created by that run.
Public releases MUST NOT be automatically deleted or overwritten.

#### Scenario: Publication succeeds
- **WHEN** every local, upload, and remote read-back check passes
- **THEN** the draft becomes a complete public prerelease automatically

#### Scenario: Publication fails before visibility
- **WHEN** draft creation, upload, or read-back verification fails
- **THEN** no partial public release is exposed and unrelated state is untouched

#### Scenario: Publish response is ambiguous
- **WHEN** the final publish request returns an uncertain response
- **THEN** automation succeeds only if exact public read-back proves completion;
  otherwise it fails and preserves public state for investigation

### Requirement: Release reruns are read-only and immutable

Before rebuilding, the workflow SHALL inspect any existing release for the tag.
An exact public release MUST be validated from its retained first-run assets,
manifests, provenance, body, target, and classification and returned as read-only
success. Any draft or conflict MUST fail. Published assets and tags SHALL NOT be
replaced in place; corrections use a new version and tag.

#### Scenario: Exact release is rerun
- **WHEN** the tag already has a complete coherent public release
- **THEN** the workflow exits successfully before builds or mutation despite new
  workflow/job IDs

#### Scenario: Existing release conflicts
- **WHEN** retained metadata or assets differ from the canonical first-run record
- **THEN** the workflow fails and preserves the existing state

### Requirement: Release notes are reviewed tracked inputs

Every release SHALL require a tracked notes file for its exact version. Notes MAY
provide human-facing summary text but MUST NOT override generated source,
artifact, checksum, provenance, workflow, or compatibility identities.

#### Scenario: Notes are valid
- **WHEN** tracked notes are present, privacy-safe, and contain no unresolved
  placeholder or conflicting generated claim
- **THEN** the deterministic renderer combines them with canonical facts

### Requirement: Runtime qualification remains proportionate

Release-tooling changes SHALL rely on automated evidence and MUST NOT invent a
new commercial playthrough or physical soak. Runtime-sensitive changes MUST
complete their separately approved qualification before the maintainer pushes a
release tag.

#### Scenario: Only release tooling changed
- **WHEN** source and normalized diffs prove no runtime behavior changed
- **THEN** protected automated validation is sufficient for release-tool landing
